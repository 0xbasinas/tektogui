# GUI framework research: what Tekto can learn

Research snapshot: 2026-11-11. This is a set of proposals, not a commitment or a claim of feature parity. Sources are the projects' own documentation and source comments, read on this date. The comparison is selective; it does not rank the frameworks overall. See [runtime opportunities](runtime-research.md) and [feature proposals](feature-research.md) for implementation slices and tests.

Tekto's reference point is [`round3-research.md`](round3-research.md): Rust and TSX share a retained scene, stable node ids, AccessKit semantics, CPU and optional GPU rendering, and an agent-facing dev server. Several older architecture and gap documents describe earlier milestones; verify current code before treating their status as current. Windows resize artifacts, real IME sessions, and cross-driver GPU behavior remain open in the round 3 document.

## Recommended order

1. **Make existing behavior measurable.** Add opt-in frame stages and surface-size traces, then reproduce the resize strip on Windows. Add an accessibility inspection and real AT-SPI smoke-test plan. These support nearly every later change.
2. **Finish text and list fundamentals.** Exercise real IME and clipboard flows, improve mixed-direction text, and give virtual rows clear focus and semantic rules. Avoid promising device behavior from headless tests alone.
3. **Add narrow app building blocks.** Prototype navigation, cancellable background work, and accessible data views against one small app. Keep each independently optional where it brings substantial dependencies.

## Evidence and limits

- **What was compared:** upstream README, API/source documentation and standards for rendering, input, semantics, lists and application lifecycle. No benchmark or independent competitive audit was performed. Upstream default branches can change; check the linked version before using a detail in an implementation decision. Taffy and wgpu upstream examples may describe APIs newer than Tekto's pinned versions.
- **What already exists:** `packages/jsx-runtime/src/index.js` implements keyed `For` reconciliation and disposal; `crates/tekto-widgets/src/lazy.rs` implements a separate fixed-height, app-synced virtual list. They solve different problems. The existing `Recording` replays explicitly supplied tree actions, not arbitrary OS events, timers or application side effects.
- **What is inferred:** the proposals and priority order are Tekto-specific judgments, not features guaranteed by any source. Neither a framework's API nor a passing local test proves its behavior on every device.
- **What is intentionally excluded:** framework adoption, a new DSL, an immediate-mode rewrite, a webview-based default, and cloning a platform design system. A source being useful to study does not make it an approved dependency.

## Decisions to make before implementation

| Decision | Small first experiment | Stop or revisit if |
| --- | --- | --- |
| Rendering and resize | Trace real physical sizes and surface results on an affected Windows system. | The strip cannot be correlated with a frame or a proposed change lacks a reproducible before/after. |
| Layout/text caching | Profile creation, measure calls and caret geometry independently; compare one bounded cache to an uncached run. | Correct invalidation cannot be demonstrated, or memory/build costs exceed a measured benefit. |
| Lists | Define key/node/focus lifetimes, then support one fixed-height Rust/TSX example. | Off-screen focus and accessibility actions cannot be represented honestly across target adapters. |
| Tasks | Prototype completion ownership and cancellation for one request. | A shared API requires a mandatory executor or leaks host-specific types into applications. |
| Navigation and data views | Build a small route stack and read-only table in a real example. | Accessibility, removal and back behavior remain ambiguous or the API needs a large new framework. |

## Boundaries

These are design observations, not instructions to copy implementation. Tekto's [agent rules](../../AGENTS.md) prohibit wrapping other engines, require the existing scene/AccessKit identity model, keep GPU and QuickJS out of defaults, and require a license review before any new direct dependency. Flutter and Masonry are comparison sources, not proposed dependencies. No external code is copied by these documents; check upstream license and attribution separately before reusing code.
